**Problemas encontrados:**
1. **(Alto) Credenciales expuestas en el JS del cliente.** El `<script>` de `index.html` incluye en texto plano un Bearer JWT completo de la API de MailerLite (`BEARER = 'eyJ0eXA...'`) y el secreto interno `SECRET = 'alas7secret2026'` usado contra `/generate-promo`. Cualquiera que vea el código fuente de la página puede extraer ambos. El JWT decodificado tiene `exp` en el año ~2126 (prácticamente no expira). Con el Bearer, un tercero podría llamar directamente a la API de MailerLite (agregar/exportar/borrar suscriptores del grupo). Con el `X-ALAS7-Secret`, podría generar códigos de promo ilimitados sin pasar por la landing.
2. **(Medio) Fallback silencioso de promo a código fijo.** Si `/generate-promo` falla o no responde, el `catch` de `showPromo()` no avisa al usuario del error — simplemente muestra el código estático `ALAS7-2026` como si fuera válido y lo aplica al link de Stripe. Si ese código no existe (o ya no es válido) en Stripe, el usuario llega al checkout con un código roto sin ninguna advertencia previa en la landing.
3. **(Bajo) Enlaces sociales sin destino real.** Los tres íconos de redes en el footer (Instagram, X, LinkedIn) usan `href="#"` como placeholder — no rompen nada visualmente pero no llevan a ningún perfil real todavía.
4. **(Informativo) No se encontraron referencias a dominios incorrectos.** No hay menciones de `alas7.mx` ni de `vitanews` en el HTML/JS. El `CNAME` está correcto (`alas7.com`).
5. **(Informativo) Sintaxis JS válida.** El bloque `<script>` embebido pasa `node --check` sin errores.

**Recomendación:** Mover el Bearer de MailerLite y el `X-ALAS7-Secret` fuera del cliente — deberían vivir solo en el proxy de Railway, y la landing debería llamar al proxy sin credenciales visibles (el proxy ya existe para eso). Además, que el fallback de `/generate-promo` muestre un aviso visible al usuario en vez de aplicar un código estático silenciosamente. Ninguno de estos dos puntos se corrigió — quedan documentados para que Alan decida.
