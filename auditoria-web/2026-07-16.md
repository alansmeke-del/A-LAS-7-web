**Problemas encontrados:**
1. **[CRÍTICO — credenciales expuestas]** El `<script>` inline de
   `index.html` (líneas ~394-396) contiene en texto plano:
   - Un JWT `Authorization: Bearer` completo usado para el `POST /subscribe`
     (probablemente un token de API de MailerLite), con `exp` codificado como
     `4933854509` — un timestamp ~ año 2126, es decir, prácticamente sin
     expiración.
   - El secreto `X-ALAS7-Secret: alas7secret2026` usado para
     `POST /generate-promo`.
   Cualquier visitante puede ver el código fuente de la página y extraer
   ambas credenciales para llamar directamente a esos endpoints/API por su
   cuenta (spam de suscripciones, generación arbitraria de códigos promo,
   posible abuso de la cuenta de MailerLite si el token tiene alcance de
   escritura). Esto ya existía en commits previos (no es de hoy), pero sigue
   vivo en `main` y es explotable ahora mismo.
2. **[Menor]** Los tres íconos de redes sociales (Instagram, X, LinkedIn) en
   el footer usan `href="#"` sin URL real — no rompen nada pero no llevan a
   ningún perfil.
3. **[Menor]** El manejo de error de `showPromo()` es silencioso: si
   `/generate-promo` falla o no responde, el catch cae a un código promo fijo
   `ALAS7-2026` y sigue enviando al usuario a Stripe con ese código
   prefilled, sin registrar ni mostrar el fallo. Si ese código no existe
   como promoción válida en Stripe, el usuario vería un error de Stripe sin
   que quede rastro de que el endpoint de promo falló.
4. **[Nota]** No se pudo hacer la verificación en vivo de sitio/pagos/promo
   por la restricción de red de este entorno (ver sección "Sitio en vivo").

**Recomendación:** (qué se debería arreglar, PERO NO SE ARREGLÓ)
- Prioridad alta: mover el Bearer token de MailerLite y el `X-ALAS7-Secret`
  fuera del JS del cliente. Deben vivir solo en el backend (el proxy de
  Railway); el frontend no debería necesitar ni el JWT ni el secreto para
  llamar a `/subscribe` o `/generate-promo` — que el proxy los inyecte del
  lado del servidor. Rotar ambas credenciales una vez movidas, ya que las
  actuales quedaron expuestas públicamente en el historial de git y en el
  HTML servido.
- Prioridad baja: reemplazar los `href="#"` de redes sociales por URLs reales
  o quitar los íconos si no hay perfiles activos todavía.
- Prioridad baja: si se quiere que este auditor confirme la salud real del
