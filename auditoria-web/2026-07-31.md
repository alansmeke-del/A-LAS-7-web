**Problemas encontrados:**
1. **[Crítico]** Bearer token de MailerLite hardcodeado en el JS del cliente
   (`index.html:395`) — credencial de API expuesta públicamente y de vida
   prácticamente infinita (`exp` ~2126).
2. **[Bajo]** El secreto `X-ALAS7-Secret` (`alas7secret2026`) para el endpoint
   `/generate-promo` también está hardcodeado en el JS del cliente
   (`index.html:393`). Es un secreto de front-end, por definición no secreto —
   cualquiera puede leerlo y generar códigos promo directamente contra el
   backend.
3. **[Bajo]** Tres links rotos/placeholder en el footer: los íconos de
   Instagram, X y LinkedIn (`index.html:321-323`) usan `href="#"` sin ningún
   handler de JS ni URL real — al hacer clic no pasa nada útil (solo saltan al
   tope de la página). (Los otros `href="#"` del sitio, en los botones
   "Gratis" de nav y footer, sí están interceptados por JS para abrir el modal
   — esos no son un problema.)
4. **[Bajo]** Manejo de errores silencioso en `showPromo()` (línea ~506-513):
   si el fetch a `/generate-promo` falla o la respuesta no es JSON válido, el
   catch cae en silencio a un código fijo `'ALAS7-2026'` sin ningún
   `console.error` ni registro. Si el endpoint de promo se cae, todos los
   visitantes recibirían el mismo código no único, sin que quede ninguna
   señal visible para detectarlo salvo revisando canjes manualmente.
5. **[Info]** Validación local: `node --check` sobre el `<script>` extraído del
   `index.html` no reportó errores de sintaxis. El `CNAME` contiene
   correctamente `alas7.com` (no `vitanews` ni `alas7.mx`). No se encontraron
   referencias a dominios inexistentes. Los assets locales referenciados
   (`assets/logo7-v2.png`, `aviso-de-privacidad.html`, `terminos.html`) existen
   en el repo.

**Recomendación:** (no corregido, solo diagnóstico)
- Rotar de inmediato el Bearer token de MailerLite expuesto en `index.html:395`
  y sacar esa llamada del cliente por completo — que `/subscribe` en el
  backend de Railway sea quien tenga el token, y que el front-end solo llame al
  proxy sin credenciales embebidas (tal como ya hace `/generate-promo` con un
  secreto simple, aunque ese patrón también debería revisarse).
- Igual, considerar mover la validación del secreto de `/generate-promo` a algo
  que no dependa de un valor fijo visible en el HTML (rate limiting por IP,
  token de sesión de un solo uso, etc.).
- Reemplazar o quitar los tres íconos sociales sin URL real en el footer.
- Agregar al menos un `console.error` (o mejor, un beacon/log al backend) en el
  catch de `showPromo()` para poder detectar caídas del endpoint de promo sin
  depender de reportes de usuarios.
- Verificar manualmente desde fuera de este entorno que `https://alas7.com/`
  responde 200 OK, dado que este auditor no pudo confirmarlo por restricciones
  de red del sandbox.
