**Problemas encontrados:**
1. **[CRÍTICO] Credenciales sensibles expuestas en el HTML público, en texto plano, visibles con "ver código fuente":**
   - Un JWT Bearer completo de MailerLite (`BEARER`, línea ~395 de `index.html`), con expiración en el año 2126 (`exp` codificado como timestamp gigante) — es decir, prácticamente no expira nunca.
   - Un secreto de aplicación (`SECRET = 'alas7secret2026'`) usado como header `X-ALAS7-Secret` contra el endpoint `/generate-promo`.
   - Cualquier visitante puede copiar este token y llamar directamente a la API de MailerLite (o al endpoint de promo) fuera del sitio, sin pasar por el formulario ni por ningún rate-limit del frontend. Esto es una fuga de credenciales de un servicio de terceros con capacidad de escritura (suscribir/gestionar contactos), no solo un detalle cosmético.
2. Manejo de errores silencioso: en `showPromo()`, si `fetch(API + '/generate-promo')` falla o la respuesta no es JSON válido, el catch simplemente asigna el código genérico `'ALAS7-2026'` sin registrar ni avisar de ningún modo que el endpoint de promoción no respondió. Si el endpoint estuviera caído, el sitio seguiría mostrando promos "exclusivas" idénticas para todos sin que nadie se entere del fallo.
3. Enlaces muertos: los tres íconos de redes sociales del footer (Instagram, X, LinkedIn — líneas 321–323) usan `href="#"` sin ningún handler de JS ni URL real. No rompen nada, pero no llevan a ningún lado — probablemente placeholders pendientes de completar.
4. Sintaxis del JS: validada con `node --check` sobre el bloque `<script>` extraído — sin errores de sintaxis.
5. `CNAME`: correcto, contiene `alas7.com` (no hay rastro del dominio antiguo "vitanews" ni de `alas7.mx`).
6. Páginas legales enlazadas desde el footer (`aviso-de-privacidad.html`, `terminos.html`) y el asset `assets/logo7-v2.png` existen en el repo — no hay 404 internos evidentes.

**Recomendación:** (no se corrigió nada, solo se documenta)
- Máxima prioridad: rotar el JWT de MailerLite y el `SECRET` de promo, y mover ambos a un proxy/backend (el propio proxy de Railway) en vez de incluirlos en el HTML/JS del cliente. El frontend estático nunca debería contener credenciales con permisos de escritura sobre una API de terceros.
- Agregar al menos un `console.warn` o telemetría cuando `/generate-promo` falla, para poder detectar si el servicio de Railway está caído sin depender de que un usuario se queje.
- Completar o quitar los links de redes sociales (`href="#"`) del footer.
